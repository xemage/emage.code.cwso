# ADR-012 — Shadow-workspace filesystem projection: materialise-to-tmpfs (eager create + inotify write-back), not OverlayFS bind-mount or FUSE

> Filename: `ADR-012-shadow-workspace-filesystem-projection.md`

- **Status**: proposed
- **Date**: 2026-08-20
- **Decider(s)**: human (decision authority — roadmap Approval §, decision 1, 2026-08-13, settled the *whether*: filesystem projection is IN v1.0); solution-architect (this record — mechanism selection and host-matrix evidence, not the whether)
- **Tasks**: C020 (this ADR), C021 (implement the projection), C022 (write-back into the git object store), C023 (lifecycle / crash-safety, explicit crash-path test), C024 (prove it end-to-end in CI); C025 (documented-fallback) is **NOT activated** by this decision — see "Decision" below
- **Requirements / Based on**: `docs/plans/plan-cwso-v1.0-roadmap.md` (blocker B2; §2.1 gate CG2; §2.5 risk 1; Approval §, decision 1); `docs/tasks/task-C020.md`; `services/cwso-git-shadow/src/main.rs:11` (the P2-1 deferral marker); `input/CWSO_ Agentic AI Orchestration Blueprint.md` §2.3, §2.4, §6.3; `sandbox/README.md`; `orchestrator/internal/sandbox/router.go`; `deploy/docker-compose.yml` (current container-hardening posture, C019); `orchestrator/internal/tools/fs_tools.go` (`pathGuard`/T194 TOCTOU-safe I/O — directly reused prior art)

## Recommendation (top line)

**GO.** The recommended mechanism is **materialise-to-tmpfs**, built as **eager materialisation of a shadow workspace's tree into a tmpfs-backed directory at workspace-creation time, with an inotify-driven write-back into the git-shadow blob store plus a periodic hash-based reconciliation pass as a fallback for missed events**. This is a **reinterpretation** of the task's literal "materialise-to-tmpfs-**on-open**" phrasing — see "A naming note, addressed honestly" below for why the literal on-open trigger is not achievable without reintroducing FUSE, and why eager-create-plus-write-back is the closest buildable equivalent.

**Rejected: OverlayFS bind-mount** (the original P2-1 plan) and **FUSE**. Both are rejected primarily because, under CWSO's current, already-reviewed-and-hardened container posture (`cap_drop: ["ALL"]`, `no-new-privileges:true`, default seccomp, on every service in `deploy/docker-compose.yml`), both require a real `mount(2)` syscall from a running CWSO process — a capability grant this project has deliberately withheld everywhere so far — and both open a materially larger, unreviewed implementation-risk surface than extending the existing `pathGuard`/`secureOpenLeaf` TOCTOU-safe path already hardened under T194. Full reasoning, including the honest uncertainty on two of the four host-matrix rows, is in "Host matrix" and "Rejected options" below.

## Context

### The gap this ADR closes

`services/cwso-git-shadow/src/main.rs:11` carries the load-bearing marker:

> `POC-DEBT (P2-1): OverlayFS bind-mount layer is deferred to Phase 4 with sandbox runners. Today, sub-agents access the virtual FS via orchestrator → sidecar IPC instead of an OS mount.`

The roadmap (`plan-cwso-v1.0-roadmap.md` B2) calls this "the largest gap": *"A coding sub-agent runs `ls`, `cat`, `pytest` — it needs a filesystem path. Without the mount, shadow workspaces are unusable by exactly the agents they exist to serve."* Gate **CG2 — Real filesystem** blocks v1.0 declaration until this closes, with C025 as the only sanctioned escape hatch, and only on proven infeasibility across the full host matrix.

### What the original design assumed

Blueprint §2.3 (*Ephemeral Shadow Workspaces via In-Memory Git Manipulation*) states the original intent plainly: *"The sub-agent perceives a standard local filesystem, which is actually virtualized via an OverlayFS mount. In this paradigm, the lower directory is a read-only projection of the base commit tree, and the upper directory captures the agent's real-time edits."* Blueprint §2.4 (*Tiered MicroVM and Container Isolation Layer*) lays out the three-plus-one-tier sandbox strategy (Docker-trusted / gVisor / Firecracker / ZeroBoot snapshots) that `sandbox/router.go` implements today. Blueprint §6.3 (*Concurrency Control and Write-Lock Contention*) states a second, narrower commitment that pulls in a different direction from §2.3's specific "OverlayFS mount" phrasing: *"Worker sub-agents are physically restricted from interacting with the host filesystem. They operate exclusively on an ephemeral virtual file system mapped directly to libgit2 (or equivalent go-git) blob objects stored purely in volatile host memory (RAM)."* This ADR reconciles both: §6.3's "volatile host memory" commitment is satisfied more directly by a tmpfs-backed (RAM-backed) projection than by an OverlayFS upperdir, which §2.3 does not itself specify as RAM-backed (it could as easily sit on host disk, e.g. under Docker's storage area, unless deliberately pinned to a tmpfs directory too). Both blueprint sections are honored by the chosen mechanism; only §2.3's specific choice of *mechanism name* is being overridden, not its *intent* (a real, `ls`/`cat`-reachable path).

### The sandbox tiering this ADR must not contradict

`orchestrator/internal/sandbox/router.go` implements a non-escalation, default-deny tier router (`TierRouter.resolve`, lines 125–150) with three real backends: `docker-trusted` (internal tooling only, gated by `AllowDockerTrusted`, non-escalable by callers — `resolveDockerTrusted`, lines 155–166), `gvisor-fast-ephemeral` (the mandatory, always-required default and fallback tier), and `firecracker-secure-isolation` (untrusted/LLM-generated code, requires KVM). Critically, `resolveFirecracker` (lines 168–175) shows that on a host without KVM, **100% of what would have been Firecracker-tier traffic silently and unconditionally routes to gVisor** (`ReasonDegradedFallback`, line 171: `if r.cfg.DegradedMode || r.cfg.FirecrackerRunner == nil`). This is not an edge case to footnote — it means host-matrix row 2 (no KVM) is not "the primary path is unavailable," it is "100% of sub-agent execution, including what the router would otherwise consider high-risk, runs under gVisor." The host-matrix analysis below treats it that way.

### The container-hardening posture this mechanism must fit inside

`deploy/docker-compose.yml` (hardened progressively through C019 and MR !132) applies, on **every** service — `workspace-check`, `jwt-secret-fix`, `orchestrator`, `git-shadow`, `merge-engine`, `rollout` — the same baseline: `cap_drop: ["ALL"]`, `security_opt: [no-new-privileges:true]`, and (for the IPC-only sidecars `git-shadow`/`merge-engine`) `network_mode: "none"`. The **only** exception granted anywhere in the file is `jwt-secret-fix`, which is narrowly granted `CHOWN`, `FOWNER`, `DAC_READ_SEARCH` (never `SYS_ADMIN`) for a one-shot, throwaway file-ownership fix — explicitly not a precedent for granting mount-capable privileges to a long-running sidecar. Directly relevant: `git-shadow`'s own service block already mounts a **tmpfs** directory (`deploy/docker-compose.yml:361-362`, `tmpfs: - /var/lib/cwso/shadow:size=128m,mode=1777`) successfully, under this exact `cap_drop: ["ALL"]` posture (`deploy/docker-compose.yml:364`). This is not a hypothetical capability — it is already-working, already-shipped configuration in this repo, and it is the single most important piece of evidence in this ADR: **Compose/the container runtime performs the tmpfs mount at container-creation time, before the container's own process ever runs with its dropped capabilities**, so `cap_drop: ["ALL"]` does not block it. OverlayFS and FUSE both require a `mount(2)` (or `fusermount`) call issued *by a running CWSO process itself*, which is a fundamentally different, currently-unsatisfied privilege requirement — see "Host matrix" below.

### Prior art this ADR builds on rather than replaces

`orchestrator/internal/tools/fs_tools.go` implements `pathGuard` (lines 65–103) plus the `*at()`-anchored, `O_NOFOLLOW`-hardened `secureResolveDirs`/`secureOpenLeaf` walk (lines 201–273), built and reviewed under T194 specifically to close a TOCTOU race between a path-safety check and the actual filesystem operation. This code is already reviewed, already tested, and already the mechanism `read_file_sync`/`write_file_sync`/`list_dir` use in production today. Any mechanism whose implementation can extend this pattern rather than invent a new one carries materially lower implementation risk — this is one of the four weighted decision-matrix criteria below, and it is the single largest differentiator between the recommended option and the two rejected ones.

## Host matrix

Verdicts: **works** / **needs-elevated-privilege** / **impossible**. All three mechanisms scored against all four required rows (12 cells, none blank). Where evidence is a citable, project-specific fact (a file, a line, a working config), it is cited. Where a claim rests on general Linux/container/SELinux semantics rather than a CWSO-specific test, that is stated explicitly — this project has run no host-matrix conformance test for any of the three mechanisms, so several cells below are honestly hedged rather than confidently asserted.

**A load-bearing architectural finding, established by reasoning (not by a project test) before the table**: for OverlayFS specifically, the actual `mount(2)` call cannot happen inside the untrusted sub-agent's own sandbox tier (gVisor's sentry does not expose the host's real mount table to the guest process even when the guest calls `mount()` itself — whatever the guest mounts stays inside gVisor's own virtual filesystem, not host-visible; a Firecracker guest's mount table is real but confined to that guest's own virtual disk). The mount must instead happen once, in a **trusted** component (`git-shadow` or a new privileged helper), producing a real host-visible directory that is then handed to whichever sandbox tier hosts a given sub-agent via an **ordinary, unprivileged bind-mount/volume** (the same mechanism Docker already uses for every volume mount in this compose file) — not by the sandboxed process calling `mount()` itself. This means the OverlayFS privilege question is about the **trusted sidecar's own hardening** (`cap_drop: ["ALL"]` on `git-shadow` today), and is **largely independent of which sandbox tier or host row is in play** — which is why rows 1 and 2 score identically for OverlayFS below. It also surfaces a genuine, unresolved implementation risk this ADR does not have a citable answer for: propagating a mount made inside one container's private mount namespace out to a host-visible path that Docker's own volume plumbing can then bind into *other* containers is a real Linux mount-propagation problem (`shared`/`slave`/`private` propagation, `mount --make-rshared`-class configuration) that no artifact reviewed for this ADR demonstrates working in this stack. This is flagged as an open risk, not asserted as solved or unsolved.

**Synthesis**: materialise-to-tmpfs is the only mechanism that scores "works" (not "needs-elevated-privilege") on all four host-matrix rows, and it is the only mechanism whose implementation risk is a bounded extension of already-reviewed code rather than a new security-sensitive surface. Its one honest weakness — a non-zero write-back latency window instead of kernel-instant consistency — is real and is called out explicitly below rather than minimized, but it does not outweigh a 12/12 "works" host-matrix result plus materially lower crash-safety and implementation-risk exposure.

## A naming note, addressed honestly

The task's third option is named "materialise-to-tmpfs-**on-open**" — implying a lazy trigger fired by the consuming process's `open()` syscall. That literal trigger is **not achievable** without an interception layer at the syscall/VFS boundary — which is exactly what FUSE (or, less plausibly, a custom LD_PRELOAD/ptrace shim) provides and this option is specifically choosing *not* to use. The mechanism recommended here is therefore a reinterpretation: **eager** materialisation of the whole shadow-workspace tree into the tmpfs directory at workspace-creation time (not lazily per file, per open), paired with `inotify`-driven write-back for files subsequently changed at the real path. This is flagged prominently, not buried, because it is a real deviation from the option's literal name that a reader approving this ADR needs to see plainly. The practical consequences: (1) tmpfs/RAM usage scales with full workspace tree size × concurrent workspace count from creation time, not with files-actually-touched, which is acceptable at v1.0's dozens-of-workspaces / KB–MB-file scale but is a real difference from a true lazy mount, stated here rather than assumed away; (2) new files the agent creates (not just edits to existing ones) need a directory-level `IN_CREATE` watch in addition to per-file `IN_MODIFY`/`IN_CLOSE_WRITE`, the same mechanism, just enumerated honestly as more surface than "existing-file edits only"; (3) Linux `inotify` has a documented event-queue-overflow failure mode (`IN_Q_OVERFLOW`) under a large write burst, which is why the periodic hash-based reconciliation pass is a required companion, not an optional nice-to-have — it is the correctness backstop for exactly this gap.

## Decision

Adopt **materialise-to-tmpfs**, implemented as eager per-workspace materialisation into a tmpfs-backed directory (extending the pattern already proven at `deploy/docker-compose.yml:361-362`) plus `inotify`-driven write-back with periodic hash-based reconciliation as a fallback for missed or overflowed events, as the mechanism that makes CWSO shadow workspaces reachable as real filesystem paths for v1.0. This closes gate **CG2**. **C025 (documented IPC-only fallback) is not activated** — this ADR is a GO, not a NO-GO; C025 remains available only if a future implementation attempt (C021–C024) surfaces evidence that materially contradicts the feasibility findings above, in which case it should be escalated to the human as a new finding, not silently invoked.

`services/cwso-git-shadow/src/main.rs:11`'s POC-DEBT comment, which names OverlayFS specifically as the deferred plan, is now stale as a *mechanism* statement (its underlying problem statement — "sub-agents access the virtual FS via IPC instead of an OS-reachable path" — remains accurate until C021 lands). Updating that comment is C021's responsibility, not this ADR's — this document does not touch source files per its file-ownership constraint, but the discrepancy is recorded here so C021 doesn't miss it.

## Rejected options — the fatal-or-acceptable flaw, stated plainly

- **OverlayFS bind-mount**: the flaw is not merely "needs more privilege," which alone might be an acceptable, grantable trade. The flaw is that granting that privilege (`CAP_SYS_ADMIN` + relaxed seccomp on the trusted `git-shadow`/helper sidecar) is necessary but **not by itself sufficient** — this ADR could not find, in any artifact reviewed, a demonstrated path for making a mount created inside one container's private mount namespace visible as a real host path that Docker's own volume plumbing can then bind into a *different* container (the sandbox tier actually hosting a given sub-agent). That is an open architecture question, not a solved one wearing an "elevated privilege" label — treated here as the fatal flaw, not an acceptable one, because it means "grant the capability" is not a complete answer even on the rows where privilege alone would otherwise be grantable.
- **FUSE**: the flaw is the combination of (a) the same unresolved privilege requirement as OverlayFS on every row, (b) a documented, FUSE-specific crash failure mode (stale/hung mountpoints on server death) that is strictly worse for automated tooling than OverlayFS's leaked-mount failure mode, since a hang can silently block a sub-agent's shell rather than error it out, and (c) a brand-new, unreviewed TOCTOU-class security surface at the FUSE protocol boundary that this roadmap's existing hardening investment (T194) does nothing to cover. Individually any one of these might be an acceptable cost; together, against an option that has none of them, the combination is treated as fatal for a v1.0-scoped decision.

## Consequences

- **Positive**: Gate CG2 has a concrete, buildable, evidence-backed path to closure that requires no new privilege grant on any host-matrix row and reuses already-security-reviewed code (`pathGuard`/`secureOpenLeaf`, T194) rather than opening new attack surface. Crash safety (C023's explicit acceptance criterion) has the simplest possible story: plain files in a tmpfs directory, no live kernel mount object to leak. The mechanism is consistent with Blueprint §6.3's "volatile host memory" commitment.
- **Negative**: Write consistency is not kernel-instant — there is a real, bounded latency window between an agent's raw `write()` at the projected path and that write landing in the git-shadow blob store, which C022 must design around (inotify plus reconciliation fallback, not inotify alone). This is a genuine, stated deviation from what a live OverlayFS/FUSE mount would have given for free. Eager materialisation means tmpfs/RAM usage scales with full workspace-tree size at creation time, not with files-actually-touched — acceptable at v1.0 scale, not free at larger scale (out of this ADR's scope per the task's explicit exclusion of performance-benchmark design).
- **Risks introduced**: `inotify` event-queue overflow (`IN_Q_OVERFLOW`) under a write burst is a real Linux limitation that, without the reconciliation fallback, could silently drop a write-back — C022 must treat the fallback as a correctness requirement, not an optimization. Three of the twelve host-matrix cells for the *rejected* mechanisms rest on general Linux/SELinux/gVisor semantics rather than a CWSO-specific test (no project artifact confirms CWSO has run on rootless Docker or an SELinux-enforcing host at all) — this doesn't block the chosen mechanism (which scores "works" on those same rows with the same caveat, but from a much lower risk baseline: plain file I/O, not a novel mount type), but it does mean C023/C024 should, where practical, add at least a smoke check on one non-mainline host configuration rather than leaving all four rows purely reasoned-not-tested going into v1.0.
- **Follow-ups**: C021 (implement per-workspace eager materialisation, extending `fs_tools.go`'s `pathGuard`/`secureOpenLeaf` pattern; also update the now-stale OverlayFS-specific wording in `services/cwso-git-shadow/src/main.rs:11`); C022 (inotify write-back + hash-based reconciliation fallback into the git object store — this is where the "not kernel-instant" trade-off from this ADR must be made correct, not just fast); C023 (lifecycle and the explicit crash-path test that empirically validates this ADR's crash-safety claims, which are reasoned here, not yet tested); C024 (prove it end-to-end in CI: `ls`/`cat`/a real test command against a shadow workspace, an edit via ordinary tooling, captured by `commit_shadow`).

## Validation

This decision is correct if: (1) C021 delivers per-workspace materialisation without requiring any new capability grant beyond what `deploy/docker-compose.yml` already permits on `git-shadow` (i.e., no `cap_add` needed) — if C021 discovers this ADR's "works" verdict was wrong and a capability grant turns out to be necessary after all, that is itself evidence this ADR's host-matrix reasoning needs revisiting, and should be escalated rather than silently absorbed; (2) C022's write-back correctly captures a raw `write()` made by ordinary tooling (not just CWSO's own `write_shadow_file` tool) within a bounded, documented latency window, and the reconciliation fallback demonstrably recovers from a deliberately-forced `inotify` overflow in a test; (3) C023's crash-path test (kill the orchestrator/git-shadow process mid-session) leaves zero orphaned tmpfs state requiring manual cleanup, confirming the crash-safety claim made by reasoning in the Decision matrix above; (4) C024's CI-run smoke test exercises `ls`, `cat`, and a real test command against a shadow workspace end to end. If any of these four contradicts a specific claim made in this ADR, that contradiction should be recorded as a finding against this ADR (a candidate for a superseding ADR), not quietly patched around in the implementation tasks.

## Reversal criteria — what would justify revisiting OverlayFS or FUSE

None of the following exist today; any one of them occurring is grounds for a new ADR proposal, not a silent reversal of this one:

1. **A concrete, tested solution to the OverlayFS mount-propagation-to-other-containers problem** flagged in "Host matrix" emerges (e.g. a demonstrated `mount --make-rshared`-class configuration that reliably exposes a trusted-sidecar-mounted overlay directory to Docker's own volume plumbing for arbitrary other containers) — at that point OverlayFS's remaining objection is purely the privilege grant, a materially smaller decision than today's combination of privilege-plus-unsolved-architecture.
2. **CWSO commits to a minimum supported kernel version** that is confirmed to support unprivileged-user-namespace overlayfs/FUSE mounts across the actual rootless-Docker/SELinux host matrix this project targets — today no such minimum is documented anywhere in this repo, which is part of why rows 3 and 4 are hedged above.
3. **The write-back latency window (Decision matrix, Sub-agent compatibility row) proves unacceptable in practice** — e.g. C024's CI smoke test or real usage surfaces agent workflows that depend on kernel-instant write visibility in a way the inotify-plus-reconciliation window cannot satisfy. At that point FUSE (not OverlayFS, given its added crash-safety cost) becomes the narrower, fresher decision worth its own ADR.
4. **gVisor's FUSE-passthrough maturity is confirmed** (the uncertainty flagged on host-matrix row 2) and found to be stable/default-enabled — this would remove one of the two open uncertainties working against FUSE, though the privilege-grant and TOCTOU-surface objections would still need to be separately resolved.
